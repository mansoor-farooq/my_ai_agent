# Ultra Agent V5 Roadmap

## Goal

Make the Mansoor Agent Team a measurable, locally portable, governed agent
runtime. V5 is a release milestone, not a claim that an AI is universally
better than a person or infallible.

## Product constraints

- Preserve the existing 15 Antigravity agent profiles and their internal IDs.
- Keep Gemini/Antigravity as the existing default path; provider adapters must
  remain optional and must not require account switching or credential workarounds.
- Preserve existing project APIs, routes, permissions, databases and business
  logic unless a separately approved task identifies a concrete defect.
- Keep the user's project source, credentials and private signing material local.
- Separate model instructions, host approval, runtime authorization and OS
  containment. One layer must not be reported as proof of another.
- Never report an unrun test, host approval, sandbox, benchmark or live install
  as verified.
- Preserve a portable setup path; probe features on each machine and state
  limitations instead of silently lowering security.

## Phase overview

| Version milestone | Focus | Status |
| --- | --- | --- |
| V5.0 | Trust boundary: action manifest, approval binding, policy decisions, effect ledger | Managed MCP path implemented, signed and release-tested; host hook health/identity attestation remains unavailable |
| V5.1 | Execution containment: machine capability probe, isolated worker, network and secret controls | Planned; OS containment not verified |
| V5.2 | Quality proof: per-agent benchmark corpus, red-team, RAG/memory and release gates | Planned; harness exists, approved corpus is missing |
| V5.3 | Portability: provider/OS adapters, installer update report, customization preservation and rollback | Planned; installer foundation exists, full matrix not verified |

V5 work starts with a phase-specific spec and acceptance tests. A phase is not
complete because its files were created: it must pass its listed release gate.

### V5.0 implementation progress — 2026-11-13 (release build)

- Added `tools/ultra-agent-v5/action-manifest.mjs`: canonical hash, exact write
  content hashes, normalized scope/check commands, policy hash, expiry and nonce.
- Added read-only MCP preparation and made the exact returned manifest mandatory
  at both the MCP and managed-runtime entry points. Runtime recomputes it and
  rejects changed writes, commands, scope, policy or project revision.
- Added a file-backed HMAC receipt authority and append-only hash-chained local
  ledger. Approval and effect transitions survive MCP process restarts; exact
  manifest, receipt, expiry, policy and effect hashes are checked on resume.
- Managed writes are reconciled after interruption at the pre-write and
  post-effect boundaries. Unknown target state blocks. Patch promotion/discard
  runs under the task lock and is replay-safe for the exact reviewed patch.
- Added mandatory verification-check validation, stable action idempotency keys,
  manager fast-path routing guidance and the bundled durable-ledger module.
- Verification: owner-signed package and Antigravity strict plugin validation
  passed; Doctor 20/20; focused build suite 187 passed, 0 failed, 6 RAG
  integration checks intentionally skipped because the explicit database gate
  was not enabled. SHA256 is recorded in the status and dated implementation
  record.
- Fixed build discovery to recognize standalone global profile roots as well as
  `agy plugin list`. The final build detected the installed team and planned
  573 file refreshes, then plugin installation was blocked because the active
  Antigravity process held the plugin directory open. Installer stopped before
  global agent profiles were synchronized; active V5 runtime is not updated.
- Close/reload Antigravity and rerun the bundled installer to complete the sync.
  No Git push was requested in this turn.
- Open: Antigravity does not expose verifiable hook-health or signed human
  identity/effect receipts; native editor/shell actions remain outside the Node
  ledger. Do not claim universal host fail-closed behavior or OS sandboxing.

## V5.0 — Trust boundary and recoverable actions

**Outcome:** Each consequential action has a stable identity, policy decision,
approval record and replay-safe result. Native host actions and managed MCP
actions have separate evidence and are described honestly.

### Work items

- [x] Define a versioned canonical action manifest. Bind project identity,
  workspace/base revision, exact paths and payload hashes, command ID/arguments,
  allowed environment/network, policy version, expiry and one-time nonce.
- [x] Complete the managed approval broker: issue a one-use,
  manifest-bound local receipt and persist it with an append-only, hash-chained
  state ledger. It does not independently attest human identity.
- [x] Enforce policy at the managed executor boundary. Reject missing, expired,
  replayed or mismatched receipts, policy drift, unsupported operations and
  required-check omissions before side effects.
- [x] Reconcile the effect ledger across interruption points: prepared,
  authorized, executing, reconciled, verified and promoted. Replaying an
  identical action is recoverable; a changed payload under the same key is rejected.
- [x] Document and test the Antigravity native-tool boundary. Hook errors,
  missing hooks and host-native editor writes must not be described as covered
  by the Node executor. Public host docs do not provide a universal hook-failure
  guarantee or signed approval/effect receipt, so native path evidence remains
  explicitly unverified.

### Acceptance gate

- [x] Approval receipt is bound to exact canonical action bytes/hash, expires,
  and cannot be replayed for another action.
- [ ] Denial, missing hook, hook error, policy mismatch and checkpoint failure
  cause no managed side effect and never return `complete`. Executor denial,
  policy mismatch and checkpoint/effect faults are covered; missing/failed host
  hook cannot be established from the current host API.
- [x] Crash/restart tests cover before, during and after side effects; identical
  retry is idempotent and changed-payload retry is blocked.
- [x] Native host writes and managed MCP writes have separate, accurate audit
  labels; no cryptographic host attestation is claimed without a supported API.

**Gate status:** managed MCP path acceptance and local release evidence are
complete. Full host-level V5.0 claim remains open until the host can attest hook
health/approval or a separate user-confirmation broker replaces that dependency.
See the dated research and implementation record in
`planner/2026-11-13-v5-0-research-and-implementation.md`.

**Required evidence:** focused node tests, managed-task fixture report, redacted
trace with action/approval/policy hashes, and a source review of the native hook
boundary.

## V5.1 — Execution containment

**Outcome:** The product reports the actual protection level available on each
machine and runs managed work with least privilege where supported.

### Work items

- [ ] Add startup capability detection for OS build, available isolation
  mechanisms, filesystem boundary, network restriction, process-tree controls
  and effective user/credentials.
- [ ] Define worker profiles: `contained`, `review-required` and `unsupported`.
  A worktree alone is not a sandbox. Missing or failed probes never fall back
  silently to a stronger label.
- [ ] Execute in an isolated worker where available (evaluate Windows
  AppContainer/Windows Sandbox and equivalent adapters). Keep V5 portable by
  making the worker an adapter with an explicit capability report.
- [ ] Default worker network to disabled; allow only policy-approved endpoints.
  Keep long-lived provider, Git and signing credentials outside the worker.
- [ ] Return a patch and evidence from the worker; promote only after separate
  review and base-revision verification.

### Acceptance gate

- [ ] Test each supported worker profile on a clean Windows 10 and Windows 11
  environment with exact build/edition recorded; add other OSes only after a
  real execution test exists.
- [ ] Red-team filesystem escape, junction/reparse point, alternate data stream,
  child-process/breakaway, environment-secret, network-egress and DNS/proxy
  cases against the actual worker boundary.
- [ ] If isolation is unavailable, report `review-required` or `unsupported`,
  block unattended high-risk actions, and retain the unsandboxed warning.
- [ ] Package installation and worker startup work without owner-specific
  absolute paths or private configuration files.

**Required evidence:** machine capability report, worker boundary tests,
network-denial evidence, clean-install test and patch-promotion report.

## V5.2 — Quality proof and specialist capability

**Outcome:** Each specialist has a defined capability contract and owner-reviewed
results rather than unsupported “best” or “human-level” claims.

### Work items

- [ ] Define a capability matrix for every profile: task types, required skills,
  allowed/forbidden scope, expected evidence, mandatory checks and known limits.
- [ ] Build 10–20 owner-reviewed real tasks per specialist, pinned to immutable
  repository revisions, with acceptance criteria and held-out cases.
- [ ] Run repeated paired comparisons: solo Gemini versus manager + routed
  specialist with identical model, task, revision, tools and limits.
- [ ] Record acceptance, first-pass success, repair success, regression,
  unauthorized side effects, human rework, latency, cost only when observed,
  model/config identity and sample count.
- [ ] Treat p95 as provisional with small samples; publish it only with adequate
  representative observations and sample counts. Do not train on hidden holdout
  cases or count synthetic fixtures as live results.
- [ ] Evaluate RAG retrieval separately from answer quality. Add source
  attribution, stale/conflicting memory, deletion/update and cross-project
  isolation cases. Keep current lexical/pseudo-vector behavior labelled
  accurately; add a learned local embedding only after measured benefit and
  license/resource review.
- [ ] Make red-team, benchmark completeness, PostgreSQL RAG integration,
  Windows tests, doctor, secret scan and package validation release gates.

### Acceptance gate

- [ ] Every published result points to a pinned task, revision, model/config,
  repeat index and reviewer disposition.
- [ ] Every specialist either meets its agreed task-specific threshold or has
  a visible limitation and is routed away from unsupported tasks.
- [ ] No benchmark report contains fabricated costs, missing samples presented
  as zero, or universal superiority claims.
- [ ] Required security cases have zero accepted unauthorized side effects.
- [ ] Required PostgreSQL integration cases run in an isolated test database;
  required skips fail the gate.

**Required evidence:** owner-approved benchmark corpus, paired reports,
red-team report, RAG evaluation and hosted CI result.

## V5.3 — Portability and reliable upgrades

**Outcome:** A recipient can install the same signed team and MCP runtime on a
supported machine without owner-only paths, while local customizations remain
visible and recoverable.

### Work items

- [ ] Pin and report provider/OS capability adapters; keep the default
  Antigravity/Gemini setup working when optional adapters are absent.
- [ ] Build a release manifest covering agent profiles, skills, rules, hooks,
  MCP server, worker and setup requirements with hashes and compatibility.
- [ ] Make installer output a clear before/after report: added, updated,
  unchanged, locally customized, skipped and blocked files.
- [ ] Preserve user-edited rules/settings; show conflicts and provide a
  tested rollback path rather than silently overwriting or silently skipping.
- [ ] Validate first install, same-version reinstall, upgrade from the current
  release, customized-profile upgrade, interrupted upgrade and rollback.
- [ ] Verify plugin activation and MCP tools after install/reload on clean
  recipient profiles; distinguish packaged from installed/active.

### Acceptance gate

- [ ] Clean install and customized upgrade pass on the supported Windows
  capability matrix; all machine-specific limitations are shown.
- [ ] Signatures and checksums validate before install; rollback restores the
  previous known-good package and user customizations.
- [ ] The package contains the runtime and configuration it advertises; no
  owner credentials, private keys or absolute source paths are included.
- [ ] Installer report proves which version and files were applied. “Already
  installed” cannot hide a package hash/version mismatch.

**Required evidence:** signed package manifest, install/upgrade/rollback
reports, clean recipient smoke test and package-content scan.

---

## V5 release decision

V5.0 must pass its trust-boundary gate before the product is labelled V5.0.
V5.1–V5.3 may ship as staged updates only with explicit capability labels.
The final V5 release requires all required gates above, a source/version
manifest, owner-reviewed benchmark results and a clean portable install.

No speed, accuracy, security or “better than human” percentage is promised
before paired benchmark evidence supports the specific claim.
